# 面试 QA 20 问

> 围绕本项目（数据分析多智能体 · Text-to-SQL · 魔改 MetaGPT）最可能被追问的 20 个问题。
> 每个回答都对应代码里的真实实现，面试时可引到具体文件。

---

## 1. 这个项目一句话说清楚是做什么的？

把一个「数据分析团队」的协作流程做成多智能体系统：用户问一句自然语言，系统让 6 个职责单一的 Agent 依次协作——需求分析 → schema linking → 规划 SQL → 真执行 SQL → 校验 → 报告——最后产出基于**真实数据**的结论，而不是 LLM 编造的数字。数据是 GH Archive 的真实 GitHub 事件流，跑在 DuckDB 上。

## 2. 为什么是「魔改 MetaGPT」而不是从零写 agent 框架？

MetaGPT 给了一个很关键的思想：**把软件公司的 SOP 显式化成多智能体的角色分工 + 共享消息池**。我借的是这个「SOP 拆角色」的思路，但把「软件公司」换成「数据分析团队」，把「写代码」换成「写 SQL + 真查数据」。底层编排我直接用 LangGraph（StateGraph + checkpoint + interrupt），不重复造轮子。核心差异化在「真执行」——LLM 生成的 SQL 真的跑库、结果结构化回流、报错回流自我修正，这是「去 toy 化」的关键。

## 3. 为什么拆 6 个 agent，而不是一个大 prompt 全部搞定？

三个原因：
1. **职责单一 = 每个 prompt 可控、可调、可测**。需求分析只需把问题翻译成指标/维度/过滤，不需要懂 SQL；报告只需读结果写结论，不需要懂 schema。
2. **可观测**。每个节点的输入输出是结构化的 Pydantic 模型，中间态（AnalysisGoal / LinkedSchema / QueryPlan / QueryResult）全部落盘可见，出问题能定位到是哪一环。
3. **可复用 + 可替换**。比如 schema linking 单独成 agent，后续要换 embedding 检索方案，只动这一个节点，其余不动。
基线 ablation 证明了这个拆分的价值：单 LLM 一次调用正确率 0%，拆开 + 结果回流后 100%。

## 4. 「真执行」具体指什么？为什么结果要结构化回流？

「真执行」= LLM 生成的 SQL 不是拿来说说，而是真的通过 DuckDB 的 `read_only` 连接执行，查出来的行和列结构化回流。为什么要结构化、不经 LLM 字符串转述：因为一旦让 LLM 把查询结果「复述」一遍，它就可能编数字——这是 single-shot 基线 0% 的根因（SQL 语法对、能跑，但答案写在看到结果之前，只能编 `12,345 条`）。所以 execute 节点直接把真实结果作为数据喂给下游的 verify/report，报告里的每一个数字都有据可查。

## 5. 你的 baseline 是 0%，怎么证明是多 agent 的功劳而不是 baseline 设得太弱？

基线设计是刻意的、且公平的：single-shot 是「单次调用同时输出 SQL 和答案」，这是最 naive 的 LLM 用法，也是大多数人第一次做 Text-to-SQL 会踩的坑。0% 不是它「弱」，而是它暴露了一个真实问题——「SQL 能跑 ≠ 结论对」。如果面试官问「改成『写 SQL→执行→再看结果写答案』两步呢」，我答：两步版本质上已经把 execute 和 report 拆开了，那就是往多 agent 走的方向；我的 ablation 要证明的正是「结果回流」这层不是可选项而是必须项。

## 6. schema linking 是什么？Text-to-SQL 为什么需要它？

schema linking 是 Text-to-SQL 的前置步骤：把自然语言问题里的实体/概念映射到数据库里具体的表和列。真实数据库常有几十上百张表，如果把全量 schema 一股脑塞进 prompt，一是 token 爆炸，二是无关表列会干扰 LLM 选错字段、产生幻觉。所以先让一个 linker agent 根据问题精筛出「必需的列 + 表间 join 关系」，只把精简后的 schema 交给写 SQL 的规划 agent。

## 7. 你的 schema linking 具体怎么实现？

三步：
1. **动态读 schema**（`app/tools/schema.py`）：运行时从 DuckDB 的 `information_schema.columns` 读真实的表名/列名/类型，再叠一份代码维护的中文列语义描述，拼成可读文本。
2. **linker agent 精筛**（`app/agents/linker.py`）：输入「问题 + 分析目标 + 完整 schema」，用结构化输出（Pydantic `LinkedSchema`）产出 `{相关表: 相关列: 理由, join_hints}`。prompt 明确要求「宁少勿多，列名必须来自给定 schema 不能编」。
3. **规划 agent 消费**：planner 只拿 linker 精筛后的表列写 SQL，prompt 里要求「只用给定列，多表用给定 join」。

## 8. 为什么 schema 要动态读 information_schema，而不是硬编码在 prompt？

硬编码的坏处是 schema 一变（加表、改列、重命名），所有 prompt 里的描述就过时了，代码和数据脱节——这恰恰是「不稳健」。动态读把「库里真实的表结构」作为单一事实来源：数据层改了，agent 自动跟随，不用改任何 prompt 代码。这是从「手搓能跑」到「工程化」的一个关键转变。中文列语义（业务含义）没法从数据库读出来，所以单独放一份元数据字典维护，表结构 + 语义分离。

## 9. 多表建模怎么设计的？为什么拆维度表？

数据原本只有一张 `events` 宽表（含 `repo_name`、`actor_login` 冗余字段）。我拆成星型：`events` 事实表（不动，保留所有列）+ `repos` 维度表（`name/owner/repo`，从 `repo_name` 用 `split_part` 拆出 owner 和 repo）+ `actors` 维度表（`login` 去重）。为什么拆：一是让 schema linking 有真实的「跨表 join」场景（比如问「哪个仓库 owner 事件最多」必须 join repos）；二是规范化消除冗余。join 关系写死在 schema 元数据里（`events.repo_name = repos.name`）供 linker 参考。

## 10. 「数据概览防幻觉」是什么？说说你踩的那个坑。

去硬编码后暴露了一个真实 bug：评估第 4 题「这两个小时里有几种事件类型」，问题本身没有显式时间（依赖上下文），结果 planner 把「这两个小时」幻觉成了 `2024-01-01`，查出来是空。根因：旧版 prompt 硬编码了 `2026-09-01`，planner 侥幸蒙对；去硬编码后这个信息丢了，需求分析 agent 没有数据时间上下文。修法：`get_overview()` 动态查 `min/max(created_at)`，把「数据覆盖 2026-09-01 00:00 ~ 01:59:59」作为数据背景注入需求分析 agent。教训：**数据的时间/规模概览也是 schema 的一部分，必须动态提供，不能假设 LLM 自己知道**。

## 11. self-repair 怎么实现的？报错如何回流？

执行节点跑 SQL 失败时，把「原 SQL + 完整报错信息」原样喂给一个 `_FixedSQL` 结构化修正 prompt，让 LLM 输出「修正后的 SQL + 修正原因」，然后重跑；`max_retry=3` 上限防死循环。关键点：一是报错**原样**回流（不经过转述，转述会丢信息）；二是修正用结构化输出（只收一个 `sql` 字段），避免自由文本里夹带解释；三是修正 prompt 里注入动态 schema，让 LLM 修的时候知道真实表列、不编字段。

## 12. human-in-the-loop 怎么做的？interrupt 底层机制？

用 LangGraph 的 `interrupt`：报告节点判断「低置信 / 校验没过」时，`interrupt(...)` 挂起整个图，把「结论 + 置信度 + 关键发现」交出来等人工决定。人工 `accept` 就继续到 END，`reject` 就回到 plan 重新规划-执行-校验-报告，带 `review_count` 上限（2 次）防死循环。底层是 checkpoint：`interrupt` 时把状态存进 checkpointer，恢复时用 `Command(resume=...)` 从断点继续。CLI 用 `input()`，后端用 HTTP 两阶段。

## 13. 持久化 checkpoint 怎么做的？为什么不用 MemorySaver？

最初用 `MemorySaver`（内存态），缺点是服务重启或换进程后会话状态全丢。换成 `SqliteSaver` 落盘到 `data/checkpoints.sqlite`。踩过的坑：`SqliteSaver.from_conn_string()` 返回的是 `with` 上下文管理器，退出即关连接，不能用于长驻服务——正确做法是 `sqlite3.connect(..., check_same_thread=False)` + `SqliteSaver(conn)`（表懒建）。写了个「重启存活」回归测试：新连接 + 新 saver 读同一文件能拿回旧状态，证明会话真的不丢。

## 14. 后端两阶段 HITL 怎么设计的？

把 `interrupt` 从 CLI 的 `input()` 变成 HTTP 两阶段：`POST /ask {question}` 触发图跑到「完成」或「触发人工复核」就返回 `{thread_id, status: done|needs_review, report?, review?}`；若是 `needs_review`，前端把 `review` 交人工确认，再 `POST /review {thread_id, decision: accept/reject}` 用 `Command(resume=...)` 恢复。`thread_id` 是 checkpoint 的会话标识，每个会话独立。FastAPI + pydantic 入参校验（decision 只收 accept/reject）。

## 15. 评估集怎么设计？为什么用「确定性关键事实对拍」而不是 LLM 判题？

12 个问题都是「答案预先算好」的聚合类问题，每题的 ground truth 是精确数字（如 PushEvent 104,834 条）。判题方式：把系统 answer 归一化（去大小写/标点/空格）后，检查「实体 + 精确数字」这些 key 是否都在——纯字符串匹配，**不引入 LLM 判题**，因为 LLM 判题有 bias（会「给面子」），且不可复现。数据分析场景要精确数字，所以用精确对拍（「大概 10 万」不算对）。

## 16. SQL 安全/守卫怎么做的？

三层：一是 DuckDB 连接 `read_only=True`，写操作被数据库直接拒绝（最底层的兜底）；二是代码层白名单校验——只放行单条只读 `SELECT/WITH`，拒绝写操作前缀（INSERT/UPDATE/DELETE/CREATE/DROP…）和多语句（分号分隔），在 `execute_sql` 入口就拦；三是上下文管理器 `with duckdb.connect(...)` 保证连接成败都关闭不泄漏。因为 SQL 是 LLM 生成的、不可信，必须按「不可信输入」对待。

## 17. LLM 调用的稳健性怎么保证？

统一封装在 `app/llm.py`：`request_timeout=60s` 防单次请求挂起拖死流水线；`max_retries=2` 对瞬时错误（网络抖动/限流）自动重试；`invoke_structured` 结构化输出失败也自动重试（LLM 返回不符合 schema 时重来）。配置走 pydantic-settings，温度越界/重试为负会 fail-fast，API key 缺失或仍是占位符时直接抛错，不带假 key 跑出诡异结果。

## 18. 踩过哪些坑？挑两个说说。

**时间戳类型**：LLM 生成 SQL 时习惯用字符串 `BETWEEN '2026-09-01 00:00:00' AND '2026-09-01 02:00:00'` 过滤，但数据列如果存成字符串，字典序比较会在边界出错、甚至返回 0 行。修法是数据层就把 `created_at` 存成 `TIMESTAMP`，靠类型系统兜底，不依赖 LLM 写对比较。**checkpoint 连接**：见第 13 问的 `from_conn_string` 上下文管理器坑。这两个坑的共性：**不要相信 LLM 会做对底层的事，把正确性交给类型系统和库的 API**。

## 19. 为什么选 DuckDB 而不是 PostgreSQL / MySQL？

场景决定的：数据是本地落盘的分析型数据（GH Archive 事件流），DuckDB 是嵌入式、列式、零运维——不用起服务，`pip install` 就能用，一个文件就是整个库，`read_only` 连接天然适合「LLM 生成的 SQL 不可信」的只读场景。PostgreSQL 更适合多用户在线事务，这里用不上。列式存储对聚合查询（count/group by）也快。

## 20. 这个项目最大的局限是什么？下一步做什么？

局限如实说：
1. **规模小**——12 问、单表聚合为主、2 小时数据，绝对数值要谨慎；但 GH Archive 公开可扩，DuckDB 列式扫描不是瓶颈。
2. **schema 还小**——3 张表，linker 的「精筛优势」还没在大 schema（几十张表）上量化验证。
3. **LLM 随机性**——单次运行，没做多次取平均。
下一步优先级：扩数据到天/周级做更大 schema 验证；加 embedding 向量检索做大规模 schema linking 的对比；前端（给后端两阶段 HITL 配一个能看报告、点 accept/reject 的界面）。
