## 标准版（4 条 bullet）

**数据分析多智能体系统（Text-to-SQL · 魔改 MetaGPT）** ｜ 2026.09 ｜ 个人项目
*Python · LangGraph · DuckDB · LangChain · DeepSeek · Pydantic*

- **【S/T】** 针对「LLM 只会生成 SQL 文本、说不出可信数据结论」的痛点，将 MetaGPT 的「软件公司 SOP」重构为「数据分析团队」，目标是从自然语言问题直接产出基于真实数据的结论。
- **【A】** 用 LangGraph 编排 5 个职责单一 Agent（需求分析→规划→执行→校验→报告），共享 state 传递上下文；执行 Agent 的 SQL 真实跑在 DuckDB 上（`read_only` 连接代码层兜底），查询结果结构化回流、不经 LLM 字符串转述，杜绝编造数字。
- **【A】** 实现 SQL 自我修复循环（报错回流→LLM 结构化修正→重跑，上限 3 次）+ human-in-the-loop（低置信 `interrupt` 人工复核，拒绝则回环重跑）；踩坑沉淀——LLM 用字符串 `BETWEEN` 比 ISO 时间戳返回 0 行，改数据层存 `TIMESTAMP` 用类型系统兜底。
- **【R】** 自建 12 问标注评估集（答案预先算好，覆盖 Top-N/占比/时间过滤/实体聚合/payload 解析）+ 单 LLM 基线 ablation：**端到端正确率 100%（12/12）vs 基线 0%（12/12）**；self-repair 对 8 条注入错误 SQL **修复率 8/8**；数据为 GH Archive 真实 GitHub 事件 108,537 条（示例：问「哪种事件最多」→ 真查库答出 PushEvent 104,834 条占 96.59%）。

## 评估结果（真实数据）

| 指标 | single-shot（单 LLM） | multi-agent（多 agent） |
|---|---|---|
| SQL 执行成功率 | 12/12 = 100% | 12/12 = 100% |
| 答案正确率（含关键事实） | 0/12 = 0% | 12/12 = 100% |
| 端到端正确率（查到且答对） | 0/12 = 0% | 12/12 = 100% |

- self-repair 压力测试：8 条故意注入常见错误的 SQL（列名/表名写错、漏引号、时间戳格式错、别名不存在），**修复率 8/8**。
- 基线 0% 的根因：单 LLM 一次调用同时生成 SQL 和答案，答案写于「看到查询结果之前」，只能编数字（`12,345 条`、`[repo_name]`、`[cnt]`、`0 条（示例结果）`）——「SQL 能跑 ≠ 结论对」。

## 示例输出（真实运行）

问：2026-09-01 00:00–02:00 这两个小时，GitHub 上哪种事件类型最多？

答：**PushEvent，共 104,834 条，占该时段全部事件（108,537 条）的 96.59%**，置信度 0.97。

> 这是 `main.py` 的真实输出：SQL 真查 DuckDB、结论引用真实数字，不是 LLM 口头编的。面试可用它证明「真执行 + 结果回流」的实际效果。

## 面试钩子（每条 bullet 对应的可深挖点）

1. **多智能体编排**：为什么拆 5 个 agent 而非一个大 prompt？state 怎么流转？校验/报告为什么是独立职责？
2. **真执行去 toy 化**：结果为什么要结构化回流、不经 LLM 字符串？`read_only` 连接的意义？——引出「single-shot 编数字」的 ablation，说明「结果回流」不是可选项而是必须项。
3. **self-repair**：报错如何回流？为什么用结构化输出修正而非自由文本？上限 3 次的意义？修复率 8/8 是怎么测的（注入错误）？
4. **human-in-the-loop**：哪些结论需要人工复核？`interrupt` 底层机制？reject 是真回环（回到 plan 重跑）还是假按钮？
5. **类型系统兜底**：为什么不信 LLM 的类型转换？ISO 时间戳字符串比较返回 0 行的坑怎么定位、怎么修？
6. **评估体系**：评估集怎么设计？为什么用「确定性关键事实对拍」而非 LLM 判题（避免判题 bias）？基线为什么设计成「单次调用」？

## 诚实说明（面试被追问时的底线）

- 所有数字真实：108,537 条事件、12 问评估、端到端 100%、self-repair 8/8、5 agent、修复上限 3 次。
- **样本量小**：12 问、单表聚合类问题、单次运行（LLM 有随机性）。结论方向性可信（多 agent 显著优于单 LLM），绝对数值需谨慎，面试如实说「小样本验证，可扩」。
- **基线公平性**：single-shot 是「单次调用同时出 SQL+答案」；若面试官问「换成『写 SQL→执行→再看结果写答案』两步呢」——答：两步版本质已把 execute 和 report 拆开，就是往多 agent 走的方向；基线的意义是证明「不做结果回流，LLM 会编数字」。
- **self-repair 在 12 问主评估里修复 0 次**（planner SQL 均语法正确），其价值由注入错误压力测试（8/8）单独证明。
- **schema 硬编码**在 prompt（单表 7 列）；真实 Text-to-SQL 的 schema linking（大 schema 选表选列）是本项目的已知简化方向。
- 数据为 2 小时演示规模，能力上限取决于「拉多少小时数据」（GH Archive 公开可扩、DuckDB 列式扫描），非系统瓶颈。
